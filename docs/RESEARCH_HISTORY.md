# Research history

Status: **historical narrative; the root README and plan own the current route,
and specifications, evidence, and scorers own exact contracts and findings**.

## Purpose

This document explains how Formation arrived at its current research question.
It preserves failed routes because they changed what the project knows. A null
result can show that a task was already easy. An invalid comparison can expose
a broken instrument. A rejected design can reveal that the runtime, rather than
the model, would have done the important work.

This is a map, not primary evidence. Follow the links for exact prompts,
budgets, artifacts, review records, and retained responses.

## The admission ladder

Formation first tried to find a model that was competent enough for ordinary
work but had a narrow, teachable gap. That search became an admission ladder.
It produced useful instrument facts, but it also delayed contact with the
developmental uncertainty the project meant to study.

### Tasks that did not engage

The first [SQLite contact](SQLITE_CONTACT_CHARTER.md) asked Composer 2.5 to solve
three exploration tasks before any lesson or validation branch could run. The
model solved all three. The contact stopped `not_engaged` after three calls.
There was no wrong experience for persistence to repair. The
[evidence record](../evidence/sqlite-nullable-antijoin-contact-20260815/README.md)
is a task-selection result, not a Formation result.

The [Python boundary contact](PYTHON_BOUNDARY_CONTACT_CHARTER.md) tested whether
Composer would treat booleans as ordinary integers because Python makes `bool`
a subclass of `int`. Composer used exact-type checks in all three exploration
calls and passed every frozen input. That contact also stopped `not_engaged`.
Its [evidence](../evidence/python-boundary-contact-20260815/README.md) showed that
the proposed gap was absent in the exact setup.

### Small-model failures and instrument repair

The [small-model admission exploration](MODEL_ADMISSION_EXPLORATION.md) moved to
local Ministral 3B and Nemotron 4B artifacts. Ministral returned a prohibited
Markdown fence on its first easy contract task. Nemotron used Python’s ordinary
`all` function, but the undisclosed restricted sandbox did not provide it.
Ministral therefore failed the declared interface; Nemotron’s result was
instrument-tainted. The retained packet is
[partial evidence](../evidence/small-model-admission-20260815/README.md), not a
clean comparison of both models.

The corrected [Nemotron successor](NEMOTRON_ADMISSION_SUCCESSOR.md) disclosed
the full execution environment and used fresh prompts. Nemotron spent most of
its 768-token allowance on internal reasoning and returned an incomplete
function. The [successor evidence](../evidence/nemotron-admission-successor-20260815/README.md)
closed that exact setup as contract-unreliable.

The [Gemma staircase](GEMMA_CONTRACT_STAIRCASE.md) then screened 270M and 1B
models on simple JSON computations. Both stopped on the first task. The 270M
model returned fenced Python. The 1B model returned a fenced array, omitted the
required object, and selected only one of two records. The
[retained screen](../evidence/gemma-contract-staircase-20260815/README.md)
separated interface failure from the still-visible computation error.

That distinction motivated the
[structured-output trial](STRUCTURED_OUTPUT_INTERFACE_TRIAL.md). A shape-only
JSON grammar removed every Markdown fence and made all four constrained replies
valid JSON objects. Every answer was still wrong. The
[paired evidence](../evidence/structured-output-interface-trial-20260815/README.md)
showed that output constraints can repair the container without repairing the
computation inside it.

The [Granite computation gate](GRANITE_COMPUTATION_GATE.md) used four fresh
filtering, update, revision, and graph tasks. Granite returned valid JSON with
the wrong value in all four calls. Its
[evidence](../evidence/granite-computation-gate-20260815/README.md) closed that
exact setup as computation-unreliable.

The final [Qwen MLX gate](QWEN_COMPUTATION_GATE.md) also failed all four tasks.
Each logical call used its one empty-content retry. JSON-shaped text appeared
in the provider’s reasoning field, but the declared action field stayed empty
on all eight attempts. The
[evidence](../evidence/qwen-computation-gate-20260816/README.md) therefore
records an interface failure, not successful hidden computation.

The admission ladder ended there. It established three useful facts:

1. Interface compliance and computational competence are separate.
2. Constrained output can repair shape without repairing thought.
3. Several exact model setups could not perform their assigned responsibility.

Those facts remain valid within their packets. They no longer require a new
model to justify developmental contact before that contact begins.

## First developmental contact

The first [exploratory developmental contact](EXPLORATORY_DEVELOPMENTAL_CONTACT.md)
used one fixed Qwen3 14B Docker Model Runner artifact. It compared no offer,
raw persistence, a runtime-authored interpretation, and a frozen explicit
lesson under one minimal action interface.

The model already solved the visible revision rule without an offer. Raw
persistence varied on mismatch probes. Both raw persistence and the authored
interpretation sometimes prompted an unnecessary rebuild when the artifact was
already current. The 27-call
[evidence record](../evidence/exploratory-developmental-contact-20260817/README.md)
contains request-conditioned observations, not a Formation effect or a harmful
model verdict.

The contact exposed the next problem: later tasks must leave some useful fact
unknown unless experience supplies it. Otherwise the experiment cannot tell
development from a capable baseline reading the current prompt.

## Calibration and selective use

The [calibration information gap](CALIBRATION_INFORMATION_GAP.md) gave that
problem a deterministic form. One external movement consequence reveals how an
opaque controller family maps its two controls to increase and decrease. Later
devices use new action names, so copying the earlier action token cannot solve
them. Another family remains unknown, and an already-correct state needs no
calibration.

The first [calibration mechanism-discovery contact](CALIBRATION_MECHANISM_DISCOVERY.md)
showed that Qwen kept assuming the first listed control meant “increase,” even
after the observed movement showed the opposite relation. A single
[Muse successor](MUSE_COUNTER_PRIOR_SUCCESSOR.md) stopped before behavior was
observed because Docker’s backend did not recognize the model architecture.
That record is infrastructure evidence only.

The final [explicit-consequence contact](EXPLICIT_CONSEQUENCE_CONTACT.md) made
the selected control slot and movement direction explicit environment facts.
Qwen then described the relation that contradicted its earlier assumption, and
the runtime’s prewritten checks marked that description eligible. Supplying the
authored or eligible description corrected later increase cases but not the
paired decrease cases. Supplying the raw occurrence did not change behavior
relative to no persistence. The
[evidence](../evidence/explicit-consequence-contact-20260817/README.md) is a
direction-asymmetric influence observation, not a Formation or transfer
finding.

That result separated availability from influence. A candidate may exist and
be eligible without causing the later model action. The distinction is
explained in [Availability to influence](AVAILABILITY_TO_INFLUENCE.md).

## A rejected shortcut

The first response to the influence problem stored a model-authored calibration
fact and gave it to a frozen generic applicator. The
[mechanism](CALIBRATION_APPLICATOR_MECHANISM.md) and
[validation draft](CALIBRATION_APPLICATOR_VALIDATION.md) looked prospective,
but two independent reviews found that the runtime would mechanically produce
the correct later action once it received the fact.

The packet could have tested caching, routing, and stale-fact governance. It
could not have tested whether the model acquired a usable competence. The
[review record](CALIBRATION_APPLICATOR_VALIDATION_REVIEW.md) closed the route
before implementation.

This rejection produced a stronger rule: the later conditional action must
remain at risk in the cold model. The harness may arrange and measure the
experience, but it may not execute the acquired relation for the practitioner.

## Phase-coupled action

The [procedural influence problem](PROCEDURAL_INFLUENCE_PROBLEM.md) and
[domain selection](PROCEDURAL_DOMAIN_SELECTION.md) led to a phase-coupled
two-action commitment. The model had to use one situated binary family profile
while acting with fresh opaque control names. A reviewed
[deterministic specimen](PHASE_COUPLED_CONTROL_SPECIMEN.md) established the
information and action surfaces before contact.

The resulting [phase-coupled contact](PHASE_COUPLED_EXPLORATORY_CHARTER.md)
completed 69 calls. Both acquisition occurrences and both model-authored
interpretations were observable. Each proposed change copied an opaque action
token from its source episode, so the frozen governor refused both candidates.
The [evidence](../evidence/phase-coupled-exploratory-contact-20260818/README.md)
contains no governed candidate-content comparison and no Formation verdict.

This moved the hard problem earlier in the process. Before the project could
study governed use, the model needed to author a reusable relation without
merely copying episode tokens.

## Occurrence accounting

[Experience-grounded authorship](EXPERIENCE_GROUNDED_AUTHORSHIP.md) separated
several possible sources of change: added experience, interpretive process,
draft replay, static instruction, and governor feedback. The reviewed
[mechanism selection](AUTHORSHIP_MECHANISM_SELECTION.md) chose occurrence
accounting. One cold call would describe the unchanged occurrence; a later cold
call would receive that exact account and author a candidate.

The [occurrence-accounting mechanism](OCCURRENCE_ACCOUNTING_MECHANISM.md) froze
eight controls for simpler explanations. Its
[strict-budget contact](OCCURRENCE_ACCOUNTING_EXPLORATORY_CHARTER.md) completed
37 calls. Direct and withheld candidates were stable and identical. Delivered
candidates varied between samples. Part of the condition that drafted and
reviewed within one response was truncated. Controls matched by byte length did
not produce prompts with the same token count. All 29 parseable candidates
failed the frozen text-form eligibility checks, mostly because they copied
episode controls; three more outputs were malformed.

The [evidence](../evidence/occurrence-accounting-exploratory-contact-20260818/README.md)
contains no available delivery-conditioned comparison. It nevertheless exposed
two different problems: model-authored reusable change remained uncertain, and
the prompt-mass and completion instruments needed repair.

## Exact-draft challenge

The [post-accounting boundary](POST_ACCOUNTING_AUTHORSHIP_BOUNDARY.md) kept the
authorship question open without treating stable or non-copying text as
success. The reviewed [route selection](POST_ACCOUNTING_ROUTE_SELECTION.md)
chose a narrower process: retain the exact first-draft output string and give it
to a later cold call with a generic challenge before governance.

The [exact-draft mechanism](DRAFT_CHALLENGE_MECHANISM.md) makes the first member
of a predeclared direct-sample list the source. The runtime cannot replace an
awkward or malformed draft. It preserves raw string delivery, delays governance
until authorship ends, and compares nine conditions that keep sampling,
repetition, static review, same-response drafting, draft replay, and prompt mass
as live explanations.

The [strict-budget charter](DRAFT_CHALLENGE_EXPLORATORY_CHARTER.md) fixes one
Qwen3 14B artifact, two fresh mirrored worlds, two samples per condition, and a
39-logical-call schedule under a 42-attempt ceiling. Its fake runner applies the
verified provider chat template and uses a pinned tokenizer to construct the
prompt-mass control without reading the source draft. Composer 2.5 and Grok 4.6
returned `RUNNER_CONFORMS` on the repaired implementation.

The one contact then completed all 39 calls without retry. World G's challenge
replies varied. World H's challenge replies repeated the source exactly. The
[evidence account](../evidence/draft-challenge-exploratory-contact-20260818/README.md)
contains no revision, withdrawal, Formation, or validation verdict. The
reviewed [post-challenge boundary](POST_CHALLENGE_AUTHORSHIP_BOUNDARY.md) named
the narrower authorship problem exposed by that null result.

## Executable prediction and the sampling boundary

The next [route selection](POST_CHALLENGE_ROUTE_SELECTION.md) replaced exact
wording with a small executable function. Every returned string remained
executable: an exact marker could introduce a conditional rule, while any
other string became a literal prediction. A frozen evaluator tested the
model-authored function on cases fixed before contact. An independent
environment issued the result that a later cold call could use when authoring
a successor.

The reviewed [mechanism](EXECUTABLE_PREDICTION_REVISION_MECHANISM.md),
[charter](EXECUTABLE_PREDICTION_REVISION_CHARTER.md), and fake-tested runner
preserved wrong, awkward, and malformed-looking outputs without screening the
model. The one contact completed 35 calls without retry and passed replay-based
integrity verification.

In World K, the first successor changed the primary prediction from wrong to
correct and repeated exactly. Its first-cycle alternative-explanation controls
did not reproduce the complete function. The same successor also lost a
correct acquisition prediction, changed a correct non-transfer prediction into
a wrong one, and solved no transfer case. World J did not reproduce the
pattern. Several byte-identical calls elsewhere returned different functions.

The [evidence account](../evidence/executable-prediction-revision-contact-20260818/README.md)
therefore retains one mixed candidate event, not a Formation result. Both
terminal verdicts are null. The reviewed
[post-contact boundary](POST_EXECUTABLE_PREDICTION_BOUNDARY.md) separates four
questions that the earlier work had allowed to blur: whether a conditional
function is available, whether external-result exposure changes authored
functions, whether any change transfers, and whether later counterevidence can
revise it.

The reviewed [route selection](POST_EXECUTABLE_PREDICTION_ROUTE_SELECTION.md)
does not answer that uncertainty by sampling successors until one is stable.
It moves the endpoint to later cold-model behavior and lets every assigned
history continue regardless of intermediate quality. Result-exposed delivery
and ablation share one exact authored intermediate; raw, withheld, static, and
no-persistence histories carry distinct foreground information. Intermediate
outputs remain mediator evidence, not admission tickets.

## Unselected lineage and the discovery correction

The next mechanism moved every assigned history into later cold-model action.
Its six paths separated no persistence, raw persistence, result-withheld
authorship, result-exposed authorship, ablation of the exact authored text, and
a static lesson. A deterministic specimen established the environment and
information paths before a four-block Qwen contact.

The first file-path command failed during Python import. It sent no model
request. The project initially treated that failure as consuming a one-use
research authorization, then wrote a separate boundary, repair decision, and
model reviews before trying again. The module-entrypoint repair was useful
engineering. Treating the failed launch as a scientific endpoint was not. It
revealed a process problem, not a fact about the Formation thesis.

After direct user authorization, the repaired runner completed all 109 calls
without retry. The six paths proposed the same action on 15 of 16 later cases.
On the remaining case, a no-persistence request and an ablation request were
byte-identical but returned different actions. That matched-control disagreement
was the same size as the only apparent branch effect. The
[evidence account](../evidence/unselected-lineage-behavior-contact-20260819-contact/README.md)
therefore supports no condition effect or Formation verdict.

The result exposes a measurement problem: a single changed action cannot carry
causal weight when the same request sometimes changes action on its own. This is
useful for designing the next contact, but it is not yet a discovery about
development.

The lab also changed its working method. Exploration now aims to discover a
thesis-relevant phenomenon with a clear question, a small stated budget, and
retained evidence. It does not require a new chain of license documents and
automatic model reviews. Strong precommitment, replication, causal controls,
and outside criticism belong to validation after repeated evidence has found
something worth validating. Operational failures remain engineering history;
they do not consume scientific questions.

This is the handoff to the current state. The root [README](../README.md) and
[plan](PLAN.md) own the current routing.

## Supporting implementation history

The deterministic runtime and harness lane developed alongside these contacts.
Its fixture-local slices now preserve exact source identity, branch conditions,
admission authority, replay constraints, shared foreground delivery, encounter
opening, activation, practice-request construction, deterministic proposal, and
action commitment. Independent review repeatedly found cases where equal-looking
objects, reset flags, alternate controllers, or incomplete lineage could bypass
the intended authority checks. The repaired code now refuses those paths.

The isolated [micro-environment](MICRO_ENVIRONMENT_CHARTER.md) also proves that
results depend on supplied state as well as action, rather than on an action
lookup table. These are computation and provenance results. They do not show
model learning.

Exact milestone status, test counts, and stopping conditions belong to the
[plan](PLAN.md). Individual contracts own their mechanisms, and the root
[README](../README.md) owns the concise project story and present boundary.
