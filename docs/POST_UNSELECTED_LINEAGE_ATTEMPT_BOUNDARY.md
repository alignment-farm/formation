# Post-unselected-lineage attempt boundary

Status: **historical process boundary; its consumed-authority interpretation is
retired; retained to explain the launch repair**.

## Current methodological status

This boundary correctly observed that the model received no request. It then
turned that operational failure into a new authority and review sequence. The
project now rejects that second move. A failure before participant contact may
justify a direct engineering repair, but it does not consume the scientific
question or create evidence about the thesis.

The text below records the rule used at the time. It does not govern future
exploration.

## The boundary

The one-use [contact decision](UNSELECTED_LINEAGE_CONTACT_DECISION.md) is
consumed. Its exact command failed during top-level import, before `main()`,
provider preflight, or participant contact. The reviewed 109-call research
packet did not begin.

Two facts must remain separate:

1. The model-call and completion budgets were not spent.
2. The authorized execution attempt was spent.

The first fact means the contact produced no evidence about Qwen or the
unselected-lineage mechanism. The second means the project may not silently
replace the command and behave as if the reviewed attempt never happened.

## What the attempt established

The attempt established one operational fact about the research machinery. A
runner can pass imported-module tests and code review while its exact
file-path entrypoint cannot import a root-level package.

It did not establish interface availability, acquisition behavior,
authorship, later action, branch differences, environment results, Formation,
validation, or a null model result. There is no runner packet and no terminal
verdict to interpret.

## Why the gates missed it

The focused suite imported `contact.unselected_lineage_behavior_contact` and
called `main()` directly. That proved behavior after module import. It did not
execute the frozen file-path command through the operating system.

The reviews checked source hashes, the command string, internal preflight,
transport order, and closure semantics. Inspection did not reproduce Python's
script-path import environment. The command was therefore bound in prose while
its launch reachability remained untested.

This is the same general distinction the project has learned elsewhere:
interface shape and substantive competence are separate. Here the runner's
internal contact contract and its launch interface were separate. Passing one
did not prove the other.

## The next problem

Before any new contact decision could be considered, the project would need a
launchability repair that proves two narrower surfaces without executing the
candidate live command.

The first surface is operating-system launch reachability. Its proof must:

- execute the candidate entrypoint in a fresh subprocess with a distinct,
  mandatory no-contact argument;
- exercise the same top-level imports and entrypoint used by the proposed live
  path;
- stop before evidence reservation, provider preflight, endpoint access, or
  live transport;
- fail if top-level imports, repository-root resolution, or package discovery
  cannot reach that stop;
- fail the test if the subprocess contains `--live` or attempts any contact-
  adjacent side effect;
- bind the exact interpreter, working directory, command bytes, source hash,
  and exit result.

The second surface is live-argument construction. A pure parser or configuration
function must accept the proposed live argument vector and return its bound
configuration under injected no-op dependencies. That test must make evidence
reservation, provider preflight, endpoint access, and transport impossible. It
does not execute the live command and must not be described as doing so.

A `--help` or dedicated no-contact mode can test the first surface. A pure
argument test can test the second. Neither alone proves both, and an import-only
unit test proves neither operating-system launch nor live-argument construction.

## Authority assigned at the time

If this boundary passes review, it may license only drafting and reviewing a
separate launch-repair decision. This boundary itself licenses no code or test
change. The later decision may compare a module-form entrypoint, a package
wrapper, or another explicit repository-root-safe launch surface and may
license the two no-contact proofs above. It may not execute any runner
subprocess containing `--live`, reserve any evidence destination, run provider
preflight, query an endpoint, construct live transport, or contact Qwen.

Under the rule then in force, even a conformant launch repair would not revive
the consumed contact decision. Another participant attempt would have required
explicit user authorization and a new independently reviewed one-use contact
decision. The current plan retains human authorization for model contact but
retires the one-use and mandatory-review machinery.

## Review question

Return `ATTEMPT_BOUNDARY_STABLE` only if this document keeps the unspent model
budget separate from the consumed authority, makes no model or Formation
inference, identifies the exact missed executable gate, and licenses only a
no-contact launch-repair decision.

Otherwise return `REVISE_ATTEMPT_BOUNDARY` with each factual error, collapsed
authority, or route that could silently become a rerun.

## Review record

Composer 2.5 first returned `ATTEMPT_BOUNDARY_STABLE`. Grok 4.6 returned
`REVISE_ATTEMPT_BOUNDARY` because the first draft asked the exact `--live`
command to prove a no-contact stop, combined operating-system launch and live-
argument parsing into one incoherent test, and licensed test implementation
directly.

The repair separated a no-contact subprocess from pure live-argument
construction, forbade `--live` in the subprocess, and limited this boundary to
drafting and reviewing a later decision. Final independent reviews returned:

- `composer-2.5`: `ATTEMPT_BOUNDARY_STABLE`
- `grok-4.6`: `ATTEMPT_BOUNDARY_STABLE`

Neither review executed a runner command, edited repository files, or contacted
the participant model.
